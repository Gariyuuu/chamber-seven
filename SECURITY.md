# SECURITY.md — Defensive Security Review

This is a defensive review of what exists in the repository as of this
audit (2026-08-06). No penetration testing, exploitation, or access to
any live/unauthorized system was performed — this is static code review
only, per the audit's constraints.

## Authentication boundaries

**There is no authentication system.** No password, no OAuth, no session
cookie, no JWT. "Identity" is:
1. A free-text display name (`localStorage["chamber-seven:name"]`),
   never validated against anything.
2. A per-seat, per-room random token (`nanoid(24)`,
   `PlayerState.token`), minted by the server on first join and echoed
   back to the client in the `welcome` message, then stored in
   `localStorage["chamber-seven:token:<roomId>"]`.

This token is the **only** server-checked credential in the entire app.
It proves "this connection previously claimed this seat in this room,"
nothing more. It is not tied to any real-world identity, is not
rotated, and has no expiry beyond the room itself becoming irrelevant.

## Authorization boundaries

- **Seat-level:** `Main.onMessage()` resolves `seat` from the
  connection ID via `seatFor()`; every game action (`fire`, `use_item`,
  `rematch`, `leave`) implicitly acts as whatever seat the current
  WebSocket connection is mapped to. There is no way to act as a
  different seat without controlling that seat's connection.
- **Host-level:** Exactly one asymmetric privilege exists — only the
  *first* `join` message for a fresh room (before the host seat is
  `connected`) can set `GameSettings`, gated by `state.settingsLocked`.
  No other host-only actions exist (any seat can `start_game` once
  everyone's connected, for example — not restricted to the host).
- **No role/permission system** beyond the above exists.

## Protected routes

None — every route (`/`, `/room/[roomId]`, `/career`, `/leaderboard`,
`/changelog`) is fully public, and the one HTTP API route
(`GET /leaderboard`) is explicitly CORS-open to any origin
(`access-control-allow-origin: *`). This is consistent with the app's
no-accounts design — there is nothing to protect a route *from*.

## Secret handling

- **`.env.local`** is gitignored (`.env*` pattern in `.gitignore`) —
  confirmed not tracked by git.
- **`VERCEL_OIDC_TOKEN`** (present in `.env.local`) is a
  platform-injected credential. **No application code was found reading
  this variable** — it appears to be an artifact of the Vercel CLI's
  local environment sync, not something the app itself depends on. Do
  not print or commit its value regardless.
- **No API keys, database credentials, or other conventional secrets**
  exist anywhere in the codebase or its configuration — there are no
  third-party services to hold credentials for.
- **`worker-configuration.d.ts`** (generated by `wrangler types`) is
  gitignored and untracked — correctly excluded, since Worker binding
  type definitions can reflect environment-specific configuration.

## Environment variables — client-exposed vs. server-only

- `NEXT_PUBLIC_PARTYKIT_HOST` — intentionally client-exposed (the
  `NEXT_PUBLIC_` prefix is required for `usePartySocket` and the
  leaderboard fetch to know where to connect). This is a **hostname**,
  not a secret — exposing it is not a security issue; it's the whole
  point of the variable.
- No server-only secret environment variables exist to accidentally
  expose.

## Input validation

- **Server-side (authoritative):** `clampSettings()` validates/clamps
  every field of an incoming `GameSettings` payload (player count,
  team mode, rounds, HP range, items-per-reload, enabled items, bot
  skill) — a malformed or adversarial `settings` object sent directly
  over the WebSocket (bypassing the UI entirely) cannot push the room
  outside valid bounds. Game actions (`fire`, `use_item`) are validated
  for phase/turn/target legality inside `state.ts` before any mutation.
- **Display name:** `.slice(0, 20)` length-capped
  (`claimSeat()`/`Leaderboard.recordWin()`), but otherwise **entirely
  unvalidated** — no profanity filter, no character restriction, no HTML/
  script-tag stripping. See "Cross-site scripting risk" below for why
  this is (mostly) not exploitable as written, and what would make it
  become exploitable.
- **Room code (join target):** `isValidRoomCode()` in
  `src/lib/roomCode.ts` restricts the client-side "Join a Table" input
  to a specific alphabet/length pattern before navigating — this is a
  UX guard, not a security boundary (the server-side room-resolution
  doesn't re-validate the code's shape; an arbitrary room-name string
  would just resolve to a different/fresh Durable Object instance,
  which is not a vulnerability, just undefined-but-harmless behavior).

## Output encoding / XSS risk

- **React's default JSX text rendering auto-escapes.** Every place a
  player-supplied string (display name, item choice via a closed enum,
  log messages built server-side by interpolating names) is rendered
  was checked — **no `dangerouslySetInnerHTML` was found anywhere in
  `src/`**. This means a display name containing `<script>` or similar
  would render as inert text, not execute — **no XSS vector was found**
  in the current codebase.
- **Caveat:** this safety currently comes entirely from "nobody uses
  `dangerouslySetInnerHTML`," not from any explicit sanitization layer.
  If a future change introduces raw HTML rendering of any player-
  supplied string (name, a future free-text chat feature, etc.), it
  would need its own sanitization — there is no existing utility for
  this in the codebase to reach for.

## SQL injection risk

Not applicable — there is no SQL anywhere in this codebase (Durable
Object storage is accessed via a key-value API, not a query language).

## CSRF protections

Not applicable in the traditional sense — there are no cookie-based
sessions and no state-changing HTTP endpoints (the only HTTP endpoint,
`/leaderboard`, is a read-only `GET`). All state-changing actions go
through an explicit WebSocket connection that a CSRF attack (which
relies on a browser automatically attaching ambient credentials to a
forged cross-origin request) cannot silently establish on a victim's
behalf in the same way it could with cookie auth.

## File upload risks

Not applicable — no file upload functionality exists anywhere in the
app.

## Webhook verification

Not applicable — no webhooks (incoming or outgoing) exist.

## Rate limiting

**None exists anywhere** — not on the WebSocket connection/message
rate, not on `join` attempts, not on the `/leaderboard` HTTP route.
Durable Objects serialize message processing per-instance, so a spam
attack cannot corrupt state, but it could:
- Degrade real-time responsiveness for legitimate players in the same
  room (message queue backpressure).
- Run up Cloudflare request-count costs at scale.
- Allow rapid leaderboard-name collision attempts (see below).

This is a real, currently-unaddressed gap if the app is ever exposed to
adversarial traffic beyond casual/hobby use.

## Admin access

No admin interface, no admin role, no privileged account type exists
anywhere in the codebase.

## Database policies

Not applicable in the traditional RLS sense (see `DATABASE.md`) — access
control is purely at the application layer (seat/connection matching),
not enforced by any storage-layer policy.

## Logging of sensitive data

- The public/private game log (`RoomState.log`/`privateLog`) contains
  player display names and gameplay actions, all of which are
  intentionally player-visible in-game — not a leak.
- `PlayerState.token` is **never** written into any log message
  (confirmed by reading every `log()`/`privateLog()` call site in
  `state.ts` — none reference `.token`).
- No server-side operational logging (e.g. `console.log` of request
  payloads) exists to leak anything to a Cloudflare dashboard log
  stream beyond wrangler's own default request logging.

## Dependency concerns

- **`npm audit` run 2026-08-06** (while regenerating the lockfile after
  removing `zustand`): 3 vulnerabilities (2 moderate, 1 high), all in
  `undici`, transitively via `wrangler`'s bundled `miniflare`. This is
  Cloudflare's *local Worker dev simulation* dependency — it runs only
  during `wrangler dev`, not as part of the deployed Worker (which runs
  on Cloudflare's own edge runtime, not `undici`) and is not reachable
  from any application code path. **Not exploitable via the live app.**
  The suggested automatic fix (`npm audit fix --force`) would
  force-downgrade `wrangler` from `4.118.0` to `4.35.0` — a large,
  unrelated breaking change to core deploy tooling — so it was
  **deliberately not applied**. Recommended real fix: wait for (or
  manually bump to) a `wrangler` release that pins a patched `undici`
  within the current major version, rather than downgrading. Re-run
  `npm audit` periodically to check whether this has resolved upstream.
- ~~`zustand` unused dependency~~ — **removed** 2026-08-06 (`TASK-006`,
  commit `71c3956`), after re-confirming via a fresh grep it was
  genuinely unused.

## Production security gaps (headline list)

1. **Leaderboard has no per-name ownership.** `party/leaderboard.ts`'s
   `recordWin(name)` keys purely by `name.trim().toLowerCase()` with no
   token/session tie-in. **Concretely:** if Player A has 10 wins under
   the name "Alice," Player B can simply type "Alice" as their own
   display name and their next win increments the *same* leaderboard
   entry — there is no way to distinguish or prevent this. Anyone can
   also grief any name they choose by winning AI-free matches under it
   (note: AI wins are explicitly excluded, so this requires an actual
   human win, which raises the effort bar somewhat, but does not close
   the gap). **Severity: low-medium** — no data loss, no access
   compromise, purely a leaderboard-integrity/social issue, appropriate
   for a lighthearted hobby leaderboard but would need real identity to
   fix properly (which requires the accounts system this project
   deliberately doesn't have).
2. **No rate limiting anywhere.** See above. **Severity: low** at
   current traffic levels; **medium** if this app ever sees organic
   growth or is linked from somewhere high-traffic.
3. **No room storage cleanup/TTL** (see `DATABASE.md`). Not a
   confidentiality/integrity issue, but an unbounded-growth,
   cost-over-time concern. **Severity: low.**
4. **Reconnect tokens never expire or rotate.** A token leaked (e.g. via
   a shared/public computer's `localStorage` not being cleared) remains
   valid for that room indefinitely, with no revocation mechanism.
   **Severity: low** — the blast radius is "control one seat in one
   ephemeral game room," not any broader account compromise, since no
   accounts exist.
5. **No dependency vulnerability scan performed** (see above).
   **Severity: unknown/unverified**, recommend running one.

## Recommended fixes (priority order)

1. Run `npm audit` (or equivalent) and address any findings — cheapest,
   highest-confidence next step, not yet done.
2. If the leaderboard is ever meant to be trustworthy/competitive rather
   than a vanity feature, that requires solving identity first (out of
   scope without an accounts system — flag to the user as a scope
   decision, don't build a partial fix that creates false confidence).
3. Add basic rate limiting on `join`/message frequency if/when the app
   sees traffic beyond casual hobby use (e.g. a simple per-connection
   message-count-per-second cap inside `Main.onMessage()`).
4. Consider a Durable Object storage TTL/cleanup job (e.g. delete room
   storage after N days of `updatedAt` inactivity) if storage growth
   ever becomes a measured concern — not urgent pre-emptively.
5. None of the above are blocking issues for the app's current
   scope/audience (casual multiplayer game, no real user data, no
   payments) — they're documented so a future session doesn't have to
   rediscover them, not because they demand immediate action.
